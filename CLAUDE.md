## Code conventions

Repo-wide TypeScript conventions — apply to every project (apps/back, apps/front, apps/site, and the libs):

- Boolean coercion: never use the double-bang !!value. Use Boolean(value) instead (e.g. return Boolean(relationship), not return !!relationship).
- Avoid optional chaining (`?.`): prefer an explicit guard. Narrow first with an if (usually an early return) and then access the value directly, instead of reaching through it with value?.prop. Reserve ?. for the rare case where an explicit guard is genuinely impractical — it is a last resort, not the default.
- Avoid `$any()` in templates: never use the `$any()` cast to bypass type-checking in an Angular template. Instead narrow the type properly — prefer a typed helper method on the component, a signal/computed that yields the correctly typed value, or a cast inside the component class before exposing it via a template binding (e.g. read `event.target` through a typed handler, not `$any($event.target).value`). Reserve `$any()` as a last resort only when a proper typed workaround is genuinely impractical, and document why with a comment.
- `readonly` fields: mark a class member readonly whenever it is never reassigned after construction (injected services, constants, config). Omit it for genuinely mutable fields, and for signal-based members (signal / computed / input / model) where it is conventionally left off.
- Single-statement guards: when an if body is a single short statement — typically a guard clause (return / throw / continue / break) — you may omit the braces and keep it on one line (e.g. if (!relationship) return false;). Keep braces for multi-statement or long bodies, and never mix a brace-less if with an else.
- `index.ts` is a barrel — exports only: an index.ts must contain nothing but re-exports (export * from './exercise-view-mode';). Never define a type, interface, enum, constant, or any other value or logic inside an index.ts. Put each definition in its own descriptively-named sibling file (one main definition per file) and re-export it from the barrel.
- `type` alias names are camelCase (lowercase first letter): every type X = ... declaration starts with a lowercase letter, mirroring @thalassic/ui's shared types (color, controlSize, buttonVariant) — e.g. export type exerciseViewMode = 'list' | 'grid';. This applies to type aliases only; `interface`s, `class`es, and `enum`s keep PascalCase.
- Module-level constants live in a `*.constants.ts`, not at the top of a component/service: hoist magic numbers, format strings, and config arrays (e.g. option lists, format tokens, timing values) out of the file that uses them into a dedicated sibling `feature-name.constants.ts` (mirror `form-item.constants.ts`, `pin-input.constants.ts`). A lone literal used once inline is fine; a *named* constant belongs in the constants file.
- Class member / section order: group class members into sections, each introduced by a `// Section` line comment directly above its members. Omit any empty section (no bare headers). `constructor` and lifecycle hooks are ordinary members but keep their slot in the order. Private injectables and private methods are prefixed with `_`. Order for components/directives: `Injections` → `Inputs` → `Outputs` → `State` → `Computed` → `constructor` → `Accessors` → `Public methods` → `Protected methods` → `Private methods` → `Lifecycle`. `State` holds plain signals / config arrays not covered by other groups. Template-bound members are `protected`, internal-only `private`, externally-consumed (public API of the component/directive) `public`.

- **Comments are timeless documentation**: write comments as present-tense documentation of the code for a future reader with no context — not as narration of the change that produced it. Avoid first/second person and change-history wording (`added`, `moved`, `now`, `for now`, `can be added later`, `as discussed`), which goes stale. Prefer "Refresh token is delivered as an httpOnly cookie" over "the refresh token was moved to a cookie".

## Frontend architecture

- Naming: always use full, descriptive names — never single-letter or abbreviated — for identifiers and class names, in TypeScript, templates, and SCSS. Write the whole word, never a shortened form. This covers `@if` aliases, @for loop variables, callback parameters, local const/let bindings, and CSS classes (e.g. program not p, index not i, event not e, button not btn, navigation not nav, previous not prev).
- Component styles: every component stylesheet must wrap all rules inside a top-level :host { } block. Never write bare selectors at the root level of a component SCSS file. The only exception is ::ng-deep blocks (e.g. for view-transition overrides), which must sit outside :host because Angular's encapsulation does not apply to them. Media queries should be nested inside their parent rule rather than declared at root.
- Style via classes, not type selectors: add a class to the element and target that (e.g. `.skeleton { }`); never style by component/element tag selector (e.g. `tls-skeleton { }`). Give the element its own class and style the class.
- Spacing — use the `--spacing-*` scale, never a raw px for padding/margin/gap: all spacing rhythm (`padding`, `margin`, `gap`/`row-gap`/`column-gap`, and layout offsets) comes from the 4px-based spacing tokens (`libs/themes/.../_spacing.scss`) — `--spacing-1` (4px), `-2` (8px), `-3` (12px), `-4` (16px), `-5` (20px), `-6` (24px), `-8` (32px), `-12` (48px) — applied as `padding: var(--spacing-3) var(--spacing-4);`. Never hardcode a px value for these properties; pick the nearest token (round half up: 6→`-2`, 10→`-3`). Raw px is reserved for genuinely fixed structural sizing that is not spacing rhythm — element `width`/`height` (a 32px icon box), `border`/`radius`, or an alignment offset computed from such fixed sizes. Those stay px and don't get tokenized.
- No redundant wrapper element: when a component's template is a single root element wrapping all of its content (e.g. program-item's outer <div>), remove that wrapper element and move its styles onto the component :host so the host element *is* the wrapper. This holds even when the wrapper is a semantic element (<aside>, <nav>, <section>, etc.): you cannot rename the host tag, so instead apply the matching ARIA role to the host (e.g. host: { role: 'complementary' } for <aside>, role: 'navigation' for <nav>) and drop the wrapper — the host keeps the semantics without the extra element. Keep an explicit wrapper element only as a last resort: when it is genuinely required for logic, or when no host role can reproduce the needed semantics.
- Forward attributes to the inner control, not the host: when a component keeps an explicit wrapper (see the rule above) and the real interactive/semantic element is *inside* the template (e.g. tls-button's inner <button>/<a>, with the host being a non-interactive tabindex="-1" wrapper), a consumer's attribute written on the host lands on the wrong element. For any attribute that must reach the inner control but cannot live on the host — accessibility attributes (aria-label, aria-labelledby, aria-describedby, …) and similar — expose a camelCase input on the component and forward it with [attr.…]="input() ?? null" (so the attribute is omitted when unset). Follow the existing convention: input<string | undefined>(undefined) named ariaLabel / ariaLabelledby (see popover, menu, loader, button). Add these inputs whenever they would genuinely help a consumer — an accessible name, description, or similar attribute that the component's role makes meaningful — rather than waiting for a specific request; the goal is a component that is accessible and usable by default. Guard only against mirroring attributes that carry no real benefit for the component. For a composite widget whose control is several elements (e.g. pin-input's separate boxes, a dropzone region, a picker trigger + panel), the accessible name belongs on a role="group" (or the appropriate container role) named via aria-labelledby / aria-label — the WAI-ARIA best practice — not duplicated onto each inner element. This concern is not limited to consumer-supplied inputs: also reflect the component's *own* state onto the inner control's ARIA. Whenever a component already owns state that has a matching ARIA attribute — validation (`invalid()` → `[attr.aria-invalid]`, `required()` → `[attr.aria-required]`), expansion/selection, etc. — forward that state to the real control (mirroring the CSS-class reflection the base already does), not just to a class. `@angular/forms/signals` drives these state signals via the `FormUiControl` contract but emits no ARIA itself, so reflecting them is the component's job. Use `[attr.aria-invalid]="invalid() ? 'true' : null"` (omitted when false); on a composite's container role, reflect only the attributes valid for that role (e.g. `aria-invalid` on a `role="group"`, but not `aria-required`). This forwarding is a wrapper-component concern only: an attribute-selector directive (e.g. [tlsButton]) sits directly on the native element, so attributes apply natively and need no input — prefer that shape when no wrapper is required.
- BEM class naming: prefer BEM for template/SCSS class names — block__element--modifier (e.g. .day-tab, .day-tab__number, .day-tab--active). Because component styles are scoped (emulated encapsulation), class names only need to be unique within the component — name blocks for their role, keep them short, and never add a redundant component-name prefix (.info, not .program-card-info).
- Nest BEM elements/modifiers under the block with `&`: in SCSS, write a block's elements and modifiers as nested &__element / &--modifier rules inside the block rather than repeating the full class at the top level. Prefer:
  ```scss
  .exercises {
    gap: var(--spacing-4);

    &--grid { /* ... */ }
    &--list { /* ... */ }
    &__skeleton { /* ... */ }
  }
  ```
  not separate .exercises, .exercises--grid, .exercises__skeleton blocks. (This nesting sits inside the component's top-level :host { } like every other rule.)

## Motion / animations

Motion is user-controllable via MotionService (libs/core), which resolves a preference (none | essential | full | system) to a motionLevel (none | essential | full) and reflects it onto <html data-motion="…">. system follows the OS prefers-reduced-motion setting (reduced → essential). Stylesheets react to that attribute; never re-implement motion preferences per component.

- Never author a bare animation/transition — every animation must be gated by tier so the user's motion level applies. Wrap it with the motion($tier) mixin from @thalassic/themes (libs/themes/.../mixins/_motion.scss), which emits :root[data-motion='…'] & selectors. Do not hand-write @media (prefers-reduced-motion) guards — the service is the single source of truth.
  - essential — small, *functional* motion that communicates state or spatial origin (panel open/close, focus). Survives reduced motion.
  - full — expressive/decorative motion (page transitions, hero motion). Only plays at the full level.
- Reusable keyframes go in a mixin partial under libs/themes/.../mixins/ (see _panel-open.scss): define the @keyframes once at the file's top level (emitted a single time when forwarded) and expose a parameterized @mixin that only applies animation / transform-origin, so including it in N components never duplicates the keyframes. Parameterize duration/easing with the --motion-* tokens (_motion.scss).
- Enter/leave in Angular — use the native animate.enter="…" / animate.leave="…" bindings (Angular 21, CSS-driven; the repo does not use @angular/animations) with classes the motion mixin emits (block--enter / block--leave). Angular defers DOM removal until the leave animation finishes, so this works even for CDK-overlay panels.
